## Questions for follow-up (cannot reach a verdict)

1. **Determinism of `extract_aspects` when PySarf raises mid-text.** Lines 268-269 catch `Exception` and `continue`. If PySarf raises on certain inputs (e.g., a single Arabic character with no diacritics) but succeeds on others, the by-aspect set for the same input across two runs could differ — but only if PySarf itself is nondeterministic, which is unknown. The fallback to "no PySarf" path is fully tested at line 21-23, but a *partial* failure path (PySarf raises on some words, not others) is not.

2. **Behavior under the new "single-word rail" path.** If `aspect_cats` is empty AND `top[0][0] == "عامة"`, the function returns `render_general_fallback(top)` BEFORE falling back to top-1 (line 474-475). But what if `aspect_cats` is empty AND top-1 is NOT `عامة` AND `full_probs` says the model is uncertain (e.g., 40%/35%/25% across three categories)? The fall-through at line 498-499 just picks `top[0][0]` regardless of confidence. There's no display of "the model is uncertain" — just a single badge with no probability. A user can't distinguish "model is 99% sure" from "model is 35% sure". This was solved in earlier versions via `result-rank-N` styling that varied with rank; the new flat rail removed that distinction.

3. **Were the v5 ambience experiment's training-set rows accidentally included in the production CSV?** The CSV has 2500 ambience rows and the README says they're for "v5 experiment" — but they sit in the same file as production labels. If `production_labels_only.csv` was derived by filtering `category != "الجو والمكان"`, that's fine; the production audit didn't verify it. Run: `cut -d, -f2 production_labels_only.csv | sort | uniq -c` to confirm 8 categories.

4. **Whether the live deployed Space's `commit 6f91ad5` actually matches `hf_space/app.py` byte-for-byte.** Production audit claims sha256 match. I did not re-verify (would require fetching the Space's hosted file). One assertion is enough but if the test runner is going to ship its results, having a third confirmation would be cheap.

5. **What happens at the `clean()` boundary for very long inputs?** Code audit's #3 was right that there's no upper bound. But beyond DoS: `clean()` is `O(n)` for each of 3 regex passes; for `n = 1MB` that's ~3M regex operations. The tokenizer is `O(192)` after truncation, but the regex passes are not — they run on the full input. Worth measuring with a 100KB string.

## Most surprising finding

**The two production auditors both concluded "ship," yet the comment in the very file they audited claims that `hf_space/app.py::apply_rescue` "Mirrors `app/ensemble_inference.py` so the Space behaves the same as the API" — and this is demonstrably false.** The Space has 5 rescue categories vs. the API's 4; the Space uses first-match `break` while the API iterates all rules; the Space applies 0.30x dampening while the API does not. The "audit-validated, 85% → 100%" docstring at line 590 cites work done against the API's rescue logic, not the Space's. Neither auditor caught this divergence because each reviewer stayed inside their assigned file. This is the kind of fact a careful TA reviewer would catch in 5 minutes by `diff`-ing the two `RESCUE_RULES` blocks.

## Ship verdict

**Ship-with-fixes.** No findings warrant blocking deployment of a portfolio project that is already live — but two of them (C-1 and C-2) are statements in the documentation and code that are not currently supported by evidence. Both are the kind of thing that turns a "good" portfolio project into a "great" one if fixed, and a "shaky" one if a reviewer probes them.

**Minimum pre-portfolio fixes (recommended before showing to a TA):**
- C-1: Either reconcile the two rescue paths or rename the Space's function to admit they diverged.
- C-2: Either separately measure the single-model accuracy or qualify the 95.05% headline.
- I-1: Add `tests/test_space_logic.py` with at least 10 pure-logic cases. Cheap; turns the "ship verdict" into a defensible one.
- I-5: Add the `assert model.config.num_labels == len(CATEGORIES)` startup check.

**Optional but high-leverage:**
- I-2 + I-3: Fix `looks_like_praise` for `ليس` and contrastive markers.
- I-6: Pin the `pysarf` git URL to a commit SHA.
- I-7: Show probabilities (or at least a tier) per rail badge.

The two prior auditors were not wrong about anything — they were each thorough within their scope. The drift between the Space and the API is the kind of thing that only a cross-file skeptic surfaces. The 95.05% attribution is the kind of thing that only a "what would a TA ask" reviewer surfaces.
